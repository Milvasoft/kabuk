## Decided and proposed

### D68 · Touchpad gestures — Decided by the user (2026-10-15)
Suggested as one of the extras and asked for by the user, who has no touchpad now and will try it later. Kabuk reads a precision touchpad through raw input (usage page 0x0D, touch pad 0x05, `RIDEV_INPUTSINK` on the bar's control window) and the HID parser (`HidP_GetUsageValue` for each finger's X, Y and contact id, `HidP_GetUsages` for its tip switch, the contact count from the top collection): nothing is hooked or injected, and the touchpad works for Windows and every program as before. Reports are put together into frames (a touchpad may split one over several reports); when the chosen number of fingers has moved 12 % of the pad one way, at least one and a half times as far as across, that is one swipe, once per gesture (`kabuk_core::gesture`, unit tests for the cases). Swipes go to the next or previous workspace (none past the first or the last), open the overview, the app grid or the launcher, or nothing. **Off by default with three fingers**, because Windows answers three- and four-finger swipes itself (switching apps, Task View, its virtual desktops) and Kabuk does not change that setting: Settings › Windows says to set Windows' own gestures to "Nothing" and has a button to Windows' touchpad page. **Not tried on a touchpad** (neither this machine nor the VM has one): the parsing of real reports waits for the user; the integration test sends the swipe the fingers would make.

### D67 · Three more looks: Pano, Izgara, Defter — Decided by the user (2026-10-15)
The user added four looks to the design page and asked for three of them; Piksel (`k`, 90s bevels) is left out. They are drawn from the same style tables as the others (`bar/style.rs`, `launcher/style.rs`, `notify/style.rs`) with the design's CSS values, and their tokens come from the page (`themes/h.toml` …, 160 contrast cases). What the CSS needs that Kabuk did not have, and how it is done:
- **Type.** Text runs can be italic and letter-spaced (DirectWrite's font style and character spacing per range). Capitals (Izgara's `text-transform: uppercase`) follow the user's language, so Turkish writes `İ` (the design page, without a `lang`, writes `I`: "LİSTESİ" where it shows "LISTESI"). Defter's small capitals are made up as the browser does for a face without them: lower-case runs as capitals at 0.7 of the size, on one baseline.
- **Pano's task list is the apps module** (D25): the same pinned and open apps, each a button with its icon and name (the name Windows' taskbar uses), the focused one on the selection surface with the accent's tick; dragging, menus and previews work as for the icons. Down a side bar only the icons show. Its start button is the all-apps button in the accent. A notice sits above a bottom bar at the bottom right.
- **Izgara's** centre sits in the middle of the room between start and end (`auto 1fr auto`), its blocks are the bar's height, and windows get square corners; **Defter's** windows get Windows' small rounded corners (its `--radius` is 3 px).
- **Kept from the design as near as Kabuk draws:** Pano's 2 px accent line under its launcher input lies under the box rather than inside its rounded border; Defter's matched letters are drawn in the accent with an underline (the design keeps the letters in the text colour and only the underline in the accent); hover backgrounds on Pano's tasks are not drawn, as for the other looks' apps.

### D65 · Layout profiles — Decided by the user (2026-10-15)
Suggested as a feature and asked for by the user: a named arrangement of programs over monitors and workspaces (`[[profile]]` with `name` and `[[profile.window]]` `exe`, `open`, `monitor` as Windows numbers it, `workspace`, `floating`), saved from the windows the shell manages now (Settings › Windows, through `query windows`, which now also tells each window's program file and what opens it again: its file, or a packaged app's `shell:AppsFolder\…`) and opened by name from the settings, the launcher ("Open the … layout") or `kabuk msg profile <name>`. ### D64 · Theme files to share — Decided by the user (2026-10-15)
Suggested as a feature (themes shared grow a community) and asked for by the user: Settings › Appearance exports the look's settings to a `.kabuktheme` file (TOML: `[kabuk-theme] format = 1, name`, then `[theme.…]` with the look, mode, accent, text size, cursors, the bar's place, height, background and colour, the gap, a gallery wallpaper and screen saver and the wallpaper's brightness) and imports one. A picture of the user's or a wallpaper created on this machine stays home. The configuration must still be valid after the import, else nothing changes (a theme from a newer Kabuk may name a look this one lacks).

### D63 · Window rules from the app's menu — Decided by the user (2026-10-15)
Suggested as a feature (a rule made where the window is, not typed in) and asked for by the user: a program's menu on the bar offers "always open floating" and "always open on workspace n" (the workspace its window is on now), each saying when it is on and taking it off again. They are the program's own rule in `[[rules.rule]]` (its file name alone, no other matcher), made, changed or removed once it says nothing, in the configuration file as the settings write it; the settings' rules page lists it, and Kabuk opens the program's next windows by it.

### D62 · A drop-down terminal — Decided by the user (2026-10-15)
Suggested as a feature and asked for by the user: `shortcuts.dropdown` (`Win+Enter`) drops a terminal down from the top of the monitor the user works on, as Quake's console, and hides it again; it stays over every workspace. `[dropdown] command` names the program (empty: Windows Terminal in a window of its own, `wt -w new`, else PowerShell) and `height` its share of the monitor's height (20-90 %, 40 by default). The window manager starts the program and takes the first terminal window that comes within ten seconds (Windows Terminal's or the console host's class; any window for the user's own command); that window stays out of the layout (it never tiles, workspaces leave it alone) and is recorded before it hides, as every hidden window is. Closed, it is forgotten and the next press starts it again.

### D60 · Hot corners — Decided by the user (2026-10-15)
Suggested as a feature and asked for by the user, as an option: `[hot_corners]` gives each corner (`top_left`, `top_right`, `bottom_left`, `bottom_right`) one of `none` (the default), `app_grid`, `overview`, `launcher`, `screen_saver`. The mouse hook of the input thread watches the moves while any corner has an action (`kabuk_core::hot_corner`): a corner counts only when no monitor goes on past it, acts once as the mouse reaches it and again only after it left, never while a button is held; it tells the bar's control window, which acts. In game mode the hook is removed, so no corner acts.

### D59 · The user arranges the app grid — Decided by the user (2026-10-15)
Asked for by the user (show, hide and rearrange the grid's apps): as on macOS, a held press or a right click edits the grid; "−" badges hide apps, a drag moves one (held at a side edge, the page turns). ### D57 · The bar's colour is the user's choice — Decided by the user (2026-10-15)

### D56 · An app grid as macOS's Launchpad — Decided by the user (2026-10-15)
Asked how hard a Launchpad would be, the user asked for it with good animations, a button on the bar and a shortcut. Kabuk's own pieces build it: the Start menu's app list (the launcher's), the launcher's icon worker (now shared, `bar::pictures`), the popups' entrance and exit, the fuzzy search. Two windows over the monitor: the chrome (the background, the search field, the dots) fades; the pages, a strip three pages wide on the compositor, zoom in as they fade (from 106 %, 220 ms, the motion rule) and slide between pages without being drawn again (a drag only moves the strip). The background is the screen taken as the grid opens with Windows Graphics Capture (about 60 ms on a device made once at start), read 16 times smaller, blurred and darkened: over the user's black wallpaper a blurred wallpaper was plain black (found by the user). Icons load on a worker; the first two pages a few seconds after the start. `Win+Shift+A` (Windows uses `Win+A`), `bar.modules.app_grid` (on by default, first on every bar), `kabuk msg apps`. The design page has no grid; its sizes follow macOS's (7 × 5 icons of 88 DIPs at most).

### D55 · The watchdog restarts a shell that stops answering — Decided by the user (2026-10-15)
Found using Kabuk: the window manager waited for a lock it held itself (it could not put the accent frame on an elevated window, Hyper-V Manager, and took the lock again to clear the record), the bar waited for the same lock, and the whole shell stood still for a quarter of an hour. The watchdog only looked for a process that ended, so nothing noticed; the emergency hotkey (owned by the watchdog) still worked. The deadlock is fixed, and clippy's `significant_drop_in_scrutinee` is denied workspace-wide so a lock held through a `match` or `if let` cannot come back. Asked whether the watchdog should also end a shell that stops answering, the user chose yes: every 5 s it sends the bar's and the window manager's windows an empty message (waiting at most 2 s, and not at all for a thread Windows already counts as hung); after 15 s and at least 3 questions without an answer it ends the shell with exit code 17, restores the desktop and starts it again, as after a crash (the 3-in-60-s budget applies). Waking from sleep alone never counts, as it is one question, not three.

### D54 · The volume panel switches the output device — Decided by the user (2026-10-15)
Asked whether the volume panel should list the output devices as Windows 11's sound flyout does, the user said yes. Core Audio lists the active outputs and the default one (documented); making another one the default has no documented call, so Kabuk uses `IPolicyConfig::SetDefaultEndpoint` on Windows' `CPolicyConfigClient`, the interface Windows' own sound settings use, unchanged since Windows 7, for every role (console, multimedia, communications). If a Windows update changes it, choosing a device fails and is logged; the panel and the volume keep working.

### D52 · An app's right-click menu is its Windows jump list — Decided by the user (2026-10-14)
The user asked for the same menu as Windows' taskbar. Windows gives other programs no call for another program's jump list, so Kabuk reads the files Windows keeps it in, named by the app id's CRC-64 under `%APPDATA%\Microsoft\Windows\Recent`: the program's own list (`CustomDestinations`: its categories, such as Chrome's "Most visited" and "Recently closed", and its tasks, such as "New window") and Windows' record (`AutomaticDestinations`, whose `DestList` stream marks the pinned entries). Each link is loaded with Windows' own `ShellLink` (title, program, arguments); frequent and recent files come from the documented `IApplicationDocumentLists`. The formats are undocumented but unchanged since Windows 7 (checked on this machine against Chrome's and File Explorer's lists); a file not understood shows only what the documented calls give. Read only: nothing is written into Windows' lists.

### D51 · Windows go to pins by app id — Decided (2026-10-14)
Reported by the user: a web app's pin (Jitsi Meet) opened a new window at every click. Its shortcut starts `chrome_proxy.exe` while its windows are `chrome.exe`'s, so matching by program never found them. Windows' taskbar groups by app id (`AppUserModelID`): the pin's comes from its shortcut (or the packaged app), the window's from its own property store. A window whose id is a pin's goes to that pin; a window whose id no pin has goes by its program as before; the browser's windows beside a pinned web app get an icon of their own.

### D50 · The volume keys are Kabuk's while it runs — Decided (2026-10-14)
Reported by the user: changing the volume showed two indicators, Kabuk's OSD and Windows' flyout. Windows' flyout cannot be turned off without changing Explorer, so Kabuk's keyboard hook (D40, out of process) takes the volume keys and the bar steps the volume itself (2 points, as Windows) and shows its OSD. While game mode pauses Kabuk's shortcuts, the keys are Windows' again.

### D49 · The genie is drawn by Kabuk on the GPU — Decided (2026-10-14)
The user found D46's genie jagged: its strips are DWM thumbnails, axis-aligned rectangles, so the funnel's edges were 22 px stairs. More strips do not help (each is a DWM call per frame: 340 strips took 15 ms a frame and the genie fell to ~18 frames), and a window region does not clip DWM thumbnails (`kabuk-win/examples/genie_region_spike.rs`: the thumbnail showed outside the region). So the genie is drawn by Kabuk: the window's picture is taken with Windows Graphics Capture (`kabuk-win/examples/capture_spike.rs` on this machine: its visible frame exactly, no capture border with `IsBorderRequired = false`, the first picture in ~5 ms) and drawn with Direct3D 11 as a mesh of 128 rows bent into the funnel (`kabuk_core::genie::rows`), 4× multisampled, on a transparent click-through window above everything, Kabuk's bars too, so the window pours over the bar into its icon. Measured: ~150 frames per genie (the strips gave ~55) at 0-4 ms of work each. Until the picture comes (a few milliseconds; a window Windows minimised itself has none) the strips are drawn, then hidden. A window minimised from the bar waits for its picture (at most 120 ms) before it minimises. The hardware device costs ~49 MB, more than the shell's idle budget, and takes ~180 ms to make, so it is made ahead on a thread of its own when the mouse rests on an app's icon (at most every 10 s) or at a genie, and let go 60 s after the last one: Kabuk is back to its idle memory when no genie plays.

### D48 · Workspaces span every monitor — Decided by the user (2026-10-14)
With two monitors each had its own 1-9 (four shown on each bar), which the user found illogical: eight workspaces for one desk. Workspace N now spans every monitor, as GNOME's and KDE's do: each monitor keeps its own windows on it, and going to N (Win+N, a click on the bar, the overview, the launcher choosing a window) takes every monitor there together. A workspace counts as occupied on every bar when any monitor has a window on it. Moving a window to N keeps it on its monitor. Rejected: Hyprland's shared pool (any workspace on any monitor, Win+N pulling it to the focused one).

### D11 · License: PolyForm Noncommercial 1.0.0 — Decided (2026-10-12)
The user's criterion: "it must not be commercializable". MIT/Apache-2.0 allow commercial use, so they are not suitable. PolyForm Noncommercial keeps the source open, allows personal/research/non-profit use and forbids commercial use (it is not an OSI-approved "open source" license; it counts as "source-available"). Text in `LICENSE.md`. Dependencies (MIT/Apache) and embedded fonts (OFL) are compatible with it; they are distributed with their own licenses. Whether the repository will be public is asked separately at the first release.

### D1 · Language and rendering: Rust + windows-rs + Direct2D/DirectWrite/DirectComposition — Decided (2026-10-12)
The user's criterion: "the best, the most performant, the lightest". Rust: no garbage collector, small binary, low RAM, memory safety. Direct access to Windows APIs via the `windows` crate. Rendering on the GPU, no runtime or browser engine.
Alternatives: C++ (same performance, riskier), C#/.NET (the user's main language but more RAM and startup time; gets close with NativeAOT), Electron/Tauri (too heavy for a bar).

### D3 · Settings app with WebView2, only while open — Decided (2026-10-12)
The settings screen design is ready and tested as HTML. Writing things like text input, scrolling, accessibility and focus management from scratch on Direct2D would take weeks. WebView2 ships with Windows 11; the process lives only while settings are open, and costs nothing once closed. The always-running parts (bar, WM, launcher) stay native. If the user wants "everything native", the alternative: settings with `kabuk-ui` as well.

### D4 · Our own small UI tree, no off-the-shelf GUI framework — Decided
The bar and launcher draw a small number of elements; frameworks like egui/iced/Slint bring a continuous frame loop, extra memory or their own window model. Our own node tree gives full control over event-driven drawing and the theme/contrast rule; it is also the basis of the plugin contract (`Node`).

### D5 · Workspaces with `SW_HIDE` — Decided (2026-10-12)
Windows of inactive workspaces are hidden, the HWND is written to the state file first, the watchdog restores them.
Alternatives: moving windows off-screen (they stay in Alt+Tab but can become visible on multi-monitor setups, and some apps save their position), undocumented cloak/virtual desktop APIs (break with Windows updates, violate the "documented APIs only" principle). The missing Alt+Tab is covered by the "open windows" source in the launcher.

### D6 · Default shortcuts are Alt-based — Decided
The design's original `Win+H/J/K/L`, `Win+1…9`, `Win+Q` cannot work: Win+L is the lock screen and cannot be captured; the others are Windows' own functions. GlazeWM and komorebi also use Alt. The design page was updated. A Win-based set is optional in settings.

### D12 · Screen saver is the existing OledSaver — Decided
The `.scr` the user wrote and uses (C#, .NET Framework 4.8) is used as is; Kabuk only selects and installs it. When the background feature arrives, the scenes are ported to GPU shaders.
**Changed by the user (2026-10-13):** OledSaver need not be kept. Until M12 Kabuk installs and drives `OledSaver.scr` (M9); with the animated wallpaper (M12) the saver is rewritten from scratch in Rust as `kabuk-saver.scr`, drawing the same scenes with the wallpaper's code, and replaces it.

### D13 · `WorkerW` approach for the animated background — Decided (2026-10-12)
There is no documented way to draw behind the desktop icons. Sending message `0x052C` to `Progman` is undocumented but widespread (Wallpaper Engine, Lively) and involves no code injection; there is no anti-cheat risk. This is the only deliberate exception to the "documented APIs only" principle, and it is used only for the animated background. If it breaks, the animated background is turned off and falls back to its static equivalent. Static backgrounds use the documented `IDesktopWallpaper`.
**M12 spike (2026-10-13, `kabuk-win/examples/workerw_spike.rs`, Windows 11 26300):** after `0x052C` (`wParam` 0xD, `lParam` 1, sent with a timeout), `Progman` has the 24H2 structure: children `SHELLDLL_DefView` (the icons) and `WorkerW` (the wallpaper). A window that is a **layered** child of `Progman`, placed right behind `SHELLDLL_DefView`, shows behind the icons and above the wallpaper: 95 % of Monitor 1 (main) took its colour on the screen, the icons and the taskbar the rest. A plain (not layered) child does not show at all (0 %), and a layered child needs the program's manifest to declare Windows 8 or later (the examples now get Kabuk's manifest from `kabuk-win/build.rs`). The pre-24H2 structure (a top-level `WorkerW` behind the one holding the icons) is coded but could not be tried on this machine.

### D14 · Kabuk's own surfaces are rasterised with WARP — Proposed (2026-10-13)
Measured in M1: a hardware Direct3D 11 device alone adds ~48 MB of private memory (the graphics driver's user-mode heaps), which makes the 40 MB budget of SPEC §8.10 impossible before any feature exists. With WARP (Direct3D's CPU rasteriser) the running shell with two bars uses 8.9 MB, and a bar redraw takes 0.4-0.8 ms of CPU instead of 0.4-1 ms. Composition stays on the GPU: DWM composes the DirectComposition swap chains as before, so DComp animations (M10) are unaffected. Kabuk draws small surfaces only when something changes, which suits a CPU rasteriser.
The renderer keeps both paths (`kabuk_ui::render::Raster`). Features that need the GPU itself — animated wallpaper shaders (M12) and the Create pipeline's frame-time checks (M13) — create a hardware device only while they run.
Alternative: hardware device for everything (simpler, but 57 MB and over budget).

### D15 · Text size factors 0.9 / 1.0 / 1.15 — Proposed (2026-10-13)
The design page offers Small / Normal / Large without sizes. Kabuk multiplies every font size of its own surfaces by 0.9, 1.0 or 1.15; bar thickness and spacing stay as the look defines them, so the larger size still fits the 30-38 px bars. Change in `kabuk_theme::resolve::TextSize::factor`.

### D16 · Bars sit on the desk colour over a wallpaper — Proposed (2026-10-13)
The design draws the bars of every look except Ada on `--desk` when a wallpaper shows (`.screen.has-wall:where(:not([data-dir="a"])) .bar`); looks with their own bar background (Ray, Rıhtım, Etkinlik) keep it. The contrast engine checks bar text against `--desk`, so without this rule light-mode text over a dark wallpaper is unreadable. Until Kabuk draws the background itself (M12), Windows' own wallpaper is always behind the bars, so the rule always applies; from M12 it applies when `[wallpaper] kind` is not plain black. Change in `bar::manager::wallpaper_behind_bars`.

### D17 · What Rıhtım's dock holds and does — Decided by the user (2026-10-13)

### D22 · How window rules match — Proposed (2026-10-13)
SPEC §2.3 lists the matchers (exe, class, title, regex) and the actions but not how they combine. Kabuk does this: every matcher a rule sets must match; an empty one matches anything. Plain text matches when it occurs anywhere in the value, ignoring case (`discord` matches `Discord.exe`); with `regex = true` the expression is searched in the value, ignoring case, so `^…$` is needed for an exact match. The exe is the file name only (`Discord.exe`), not the path. Rules apply in order, the built-in ones first: `float` and `ignore` add up, and for workspace, monitor, minimum width and placement a later rule overrides an earlier one, so a user rule can change what a built-in rule does. A rule whose regex does not compile is reported by the configuration check and left out. Rules apply when a window opens; a rule added later applies to windows that open after it. `placement` applies only to floating windows and puts the window against that edge of the work area, one gap away, at the size it opened with (shrunk to fit). Code: `kabuk_core::rules`, `kabuk_layout::spot_rect`.

### D23 · Grabbing windows with Alt and the title double click — Proposed (2026-10-13)
SPEC §2.2 says Alt + left drag moves and Alt + right drag resizes a window from anywhere on it, and a double click on a floating window's title tiles it again. Details Kabuk chose:
- Only the **left** Alt grabs, and not while Ctrl is down: the right Alt is AltGr on the Turkish Q keyboard (Ctrl+Alt) and must keep typing `@`, `€`, `{` and so on.
- Input made by programs (remote desktop tools, automation) is never grabbed.
- When a grab starts, Kabuk presses an unassigned key (`0xE8`) once, so that releasing Alt later does not open the program's menu (ARCHITECTURE §14, AutoHotkey's "mask key").
- A window let go after an Alt grab always floats where it is, whatever "Drag to float" says (that setting is about title-bar drags). A resize keeps the frame at least 160 × 100 physical pixels and moves the corner nearest to where it was grabbed.
- Maximised and minimised windows are not grabbed (Windows owns them); windows Kabuk does not manage are never grabbed.
- The double click is recognised with Windows' own double-click time and distance; the window is asked (`WM_NCHITTEST`, at most 50 ms) whether the second click is on its title bar. That click and its release are kept from the program, so Windows does not maximise it.

**Question for the user:** Alt + click is also a shortcut inside some programs (Blender's loop select, VS Code's extra cursors, Photoshop's eyedropper). **Decided by the user (2026-10-13): rules exempt programs.** A window rule's `no_grab = true` leaves that program's Alt + clicks to it; the default rules exempt Blender, VS Code and Photoshop.

### D24 · Launcher entries and their order — Proposed (2026-10-13)
SPEC §2.5 lists the sources; Kabuk does this with them:
- **Order before typing:** open windows (the front one first, so it works like Alt+Tab), then installed apps, system commands, recent items, files from the indexed folders, bookmarks. Typing ranks everything by the match: letters next to each other, at the start of the title (worth most) or of a word count more; equal scores go by the Turkish alphabet. The calculator's result, when the text is a calculation, is always first.
- **When sources are read:** open windows when the launcher opens; the rest on a worker thread the first time it opens and again when they are older than five minutes, so Kabuk spends nothing on them while idle. Until the first gathering is done (about 1.5 s with 949 entries on this machine) the launcher shows windows and commands, and the rest appear as they arrive.
- **Indexed folders** are walked breadth first, six levels deep and 5,000 entries at most; hidden folders and `node_modules`, `target`, `bin`, `obj` are skipped.
- **Recent items:** the 100 newest of Windows' recent items whose target still exists.
- **Bookmarks:** Chrome and Edge, every user profile, web links only.
- **Commands** run at once, as Start's power menu does (no confirmation for restart or shut down).
- **Icons:** each row shows its kind's icon, as the design page does; programs' own icons are a later improvement.

### D42 · System theme: Windows itself follows the look — Decided by the user (2026-10-14)
**Outcome (2026-10-14, after trying it on the user's machine): only the colour layer survives.** The **Explorer** and **icon** layers were built and then removed because Windows 11 26300 gives no safe way to make them visible.
- **Explorer:** the safe, documented approach (DWM caption/immersive-dark + uxtheme app-mode) produced no visible result — File Explorer draws its own tabbed title bar and its content in XAML, so `DWMWA_CAPTION_COLOR` does nothing and dark mode is already set by the colour layer; `SetWindowTheme` on the frame broke the XAML layout instead. The only way to actually theme Win11 Explorer is the risky XAML/inline-hook path (Windhawk-style), which breaks on Windows updates and carries anti-cheat risk; the user chose to drop it.
- **Icons:** the user-found key bug was fixed first (This PC and the Recycle Bin also written to the per-user `…\Explorer\CLSID\{clsid}\DefaultIcon` the desktop reads, not only `Software\Classes\CLSID`). But on 26300 **no registry override showed**: the per-user `Explorer\CLSID` override is ignored for the desktop and nav-pane icons, and the machine-wide `HKLM\…\Shell Icons` folder/drive override is ignored too — confirmed with a UAC-elevated write plus an icon-cache clear and an Explorer restart. The only working folder-icon mechanism is per-folder `desktop.ini` (what Windows' "Customize" and FolderIco use), which cannot theme every folder; the one global way is patching `imageres.dll`, which Kabuk will not do. Store-associated file types take their icon from the app package, so their override never wins either. The user chose to drop the icon layer too.
- **Colours** stay and work (Windows' mode and accent follow the look). The original decision follows, for the record.

The user asked whether Kabuk could restyle all of Windows, from the folder icons on, and chose to have every layer, each one turned on and off on its own, with code injection into Explorer for what cannot be reached otherwise. This is a deliberate exception to CONTRIBUTING.md rule 4 and ARCHITECTURE principle 2, limited to `explorer.exe` (D43 for anything beyond). The layers, under `[system_theme]` in `kabuk.toml`, each a switch in Settings → Appearance → "System theme" (all off by default, proposed):
- **Colours** (`system_theme.colors`): Windows' app and system mode (`AppsUseLightTheme`, `SystemUsesLightTheme`) follow Kabuk's mode, and Windows' accent colour (the `Accent` and `DWM` keys under `HKCU`) follows the look's accent, adapted by the contrast rule (SPEC §4); Windows is told with `WM_SETTINGCHANGE` ("ImmersiveColorSet"). Only documented, per-user values. Built (2026-10-14): `AppsUseLightTheme`, `SystemUsesLightTheme`, `AccentPalette` (seven shades from the accent, Windows' eighth colour kept), `AccentColorMenu`, `StartColorMenu` and the DWM's `AccentColor`; the DWM's colorization words are left to Windows, which copies the accent into them late after each change. All eight are recorded, the colorization words too: that late copy otherwise replaced a title bar colour the user kept apart from the accent (found on the user's machine: red became the accent's grey), so a restore writes the DWM's words back after the others and keeps writing them for two seconds, off the bar's thread.
- **Icons** (`system_theme.icons`): a set of icons per look, drawn by Kabuk from the look's tokens (closed and open folder, drives, This PC, the Recycle Bin empty and full, and the common file kinds: text, image, audio, video, archive, code, PDF, program, other), written as `.ico` files into the state folder and made anew when the look, mode or accent changes. Folder and drive icons through `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Shell Icons`, which needs administrator rights: Kabuk asks once through a UAC prompt (a short elevated `kabuk.exe --system-icons apply|restore`), and needs it again to restore. File kinds through `HKCU\Software\Classes\<ProgID>\DefaultIcon` on the ProgID each extension resolves to now (`AssocQueryString`), and This PC and the Recycle Bin through their per-user `CLSID\…\DefaultIcon`. When a program writes its own icon back (an update or a reinstall), Kabuk notices it from a change notification on the key (`RegNotifyChangeKeyValue`, no polling) and sets its own again. Icon caches are refreshed with `SHChangeNotify(SHCNE_ASSOCCHANGED)`. Known limit: in the large icon views Explorer draws a folder with a preview of its contents, which ignores `Shell Icons`; the Explorer layer draws those.
- **Sounds**: not built; Windows' own sounds stay (D44, decided by the user).
- **Explorer** (`system_theme.explorer`, marked experimental): `kabuk-explorer.dll` is loaded into `explorer.exe` and draws File Explorer's inside (list, tree, status bar, menus and the context menu, its dialogs, its toolbar, address bar and tabs, the folders with a preview) in the look's tokens. Win32 parts by hooking the theme drawing functions Explorer calls (`uxtheme`'s `DrawThemeBackground`, `DrawThemeText`, `GetThemeColor` and their kin, `GetSysColor`); the XAML parts of Windows 11's Explorer through `InitializeXamlDiagnosticsEx` (the documented diagnostics entry used by TranslucentTB and Windhawk's styler), which sets their brushes and resources. Safety, all of it required:
  - Only `%WINDIR%\explorer.exe` processes of the user's own session are touched; `kabuk-win`'s loader refuses any other image (tested). No global hook, nothing in any other process.
  - The DLL hooks nothing on a Windows build it was not tried on (a list of tried builds of `explorer.exe`, `uxtheme.dll` and `Windows.UI.Xaml.dll`); Kabuk says so and Settings offers "Try anyway" once.
  - Every hook calls the original on any error, and a panic inside a hook is caught, turns that hook off and never reaches Explorer.
  - The DLL waits on Kabuk's process handle and removes its hooks and unloads itself when Kabuk ends in any way, crashes included, so nothing stays even if the watchdog fails. Turning the switch off, exiting and `kabuk --restore` tell it to unload; `--restore` restarts Explorer if it does not answer in time.
  - If Explorer ends abnormally twice within a minute of the DLL being loaded, the layer turns itself off and the user is told.
  - When Explorer restarts, the DLL is loaded again after its windows are back.
  - In game mode the DLL is unloaded by default (`system_theme.explorer_in_game = false`) and loaded again afterwards; tried with League of Legends (Vanguard) by hand before the layer leaves experimental.
  - The look's tokens reach the DLL through a read-only shared memory block made by Kabuk and an event that signals a change; the DLL never reads files, the network or the registry.
Every changed value is recorded in the state file before it is written and written back on exit, when its switch is turned off, by `--restore` and by the watchdog (CONTRIBUTING.md rule 5). The `HKLM` icon values need the UAC prompt to come back; after a crash the watchdog cannot show one, so they come back at Kabuk's next start or `kabuk --restore` (a folder icon may stay Kabuk's until then; the user knows). D30's title bars and corners stay as they are and complete the picture.

### D38 · Installing for the user (M14) — Proposed (2026-10-13)
`kabuk --install`, run from the folder of a build or a release, needs no administrator rights: it copies the four programs to `%LOCALAPPDATA%\Programs\Kabuk`, puts "Kabuk" (the watchdog, which starts the shell) and "Kabuk Settings" in the user's Start menu, and writes an uninstall entry under `HKCU`, so Windows' "Installed apps" lists it. It asks whether Kabuk should start at sign-in (ARCHITECTURE §2: only the watchdog, under `HKCU\…\Run`, never without consent); `--startup on|off` answers without asking and changes it later. `kabuk --uninstall` (what "Installed apps" runs) first undoes everything as `--restore` does, removes the stored API keys, the shortcuts, the uninstall entry and the sign-in value, and deletes the program folder once it has ended; the settings and the state folder stay, so installing again keeps them. Tests install into a temporary folder and a registry key of their own (`--debug-install-root`, test builds only).

### D37 · How created wallpapers are made and checked (M13) — Proposed (2026-10-13)
SPEC §9 names the format and the checks without their exact terms. Kabuk's choices:
- **The shader is one function.** `wall.hlsl` defines `float3 wall(float2 px)` (the pixel's position from the top-left); Kabuk writes the rest of the pixel shader: a constant buffer with `time`, `resolution`, the user's brightness, eight of the look's colours as `tok_accent`, `tok_accent2`, `tok_desk`, `tok_fg`, `tok_dim`, `tok_surf`, `tok_trace`, `tok_trace_strong`, and up to eight adjustable values by their names; the colour returned is clamped, made opaque and scaled by the brightness. Textures, samplers, buffers, registers, `#include`, `#pragma`, `discard` and `clip` are refused before compiling.
- **No frame can hang the GPU.** The compiled code may have no dynamic flow control (every loop unrolled, so it has constant bounds) and at most 4096 instructions, read with `D3DReflect`; each pixel's work is bounded, so there is nothing to cancel before Windows' GPU timeout. A compiler message loses the working folder before it goes to the model (it named the user's folder).
- **The OLED checks in numbers.** A minute of the wallpaper's time is drawn as 61 frames at 960 × 540, each averaged down to 192 × 108 cells of brightness (Rec. 709 weights): the background is black when at least half the cells, over all frames, are under 2 %; the average must be at most 8 %; a cell is still and bright when it stays at 25 % or more and changes by less than 5 % over the minute, and such cells may cover less than 0.1 % of the picture (a single still star passes). Frame time: the slowest of 120 frames at 3840 × 2160, at most 4 ms. They are checked at full brightness in the look's dark colours, which is also what plays.
- **The models.** Claude `claude-opus-5-5`, OpenAI `gpt-5` (one constant each in `kabuk-wallgen::providers`); for Ollama, the first installed model made for code, else the first installed. Answers may take five minutes.
- **Keys** are typed into a password field (no autofill) and stored as generic credentials named after the Kabuk instance (`Kabuk/<instance>/wallgen/<provider>`), so a test's Kabuk never touches the user's key.
- **Kept on Apply.** A created wallpaper is written to the state folder (`walls/gen-<seconds>/`) only when the user applies it; Try again makes a new one.

### D36 · The built-in scenes are Rust vector scenes in their own process — Proposed (2026-10-13)
ARCHITECTURE §11b planned one HLSL pixel shader per scene. OledSaver's scenes are simulations with state (the circuit eye routes traces cell by cell on a grid, keeps them from touching, sends signals along them and moves the eye's pupil after them), which a stateless pixel shader cannot hold. So the built-in scenes are ported as pure Rust simulations (`kabuk-scenes`, unit-tested against OledSaver's behaviour) drawing lines, circles, text and the wordmark through a small canvas, and Direct2D draws them on the hardware GPU. They run in their own process, `kabuk-saver.exe`, which is both the screen saver (installed as `kabuk-saver.scr`, replacing OledSaver.scr as D12 planned) and, with `--wallpaper`, the animated wallpaper behind the icons (D13): a hardware Direct3D device costs ~48 MB (D14), which the shell's 40 MB budget cannot carry, and a scene that fails cannot take the shell down. Created wallpapers (M13) stay shaders, as SPEC §2.10's format says.

### D35 · Window moves are animated with DWM thumbnails — Decided by the M10 spike (2026-10-13)
`kabuk-win/examples/thumbnail_spike.rs` tried ARCHITECTURE §7 on this machine (Windows 11 26300, Monitor 1 (main) at 360 Hz): two `kabuk-testapp` windows swap places while a black, click-through (layered, transparent to input) overlay over the monitor shows their live DWM thumbnails moving from the old places to the new ones with the cubic ease-out over 200 ms, and the real windows jump once underneath. In 8 runs: 72-73 frames per 200 ms (one per refresh, 2.8 ms apart, longest gap 5.9 ms), no frame missed or dropped by DWM, and the thumbnail is on screen mid-move (the screen read at its title bar is lit, as the real window's is before the overlay). So window transitions use this approach; heavy programs (browsers, IDEs) are still to be tried by hand, as they only have to repaint once at their new size.
**Under the windows (M12 spike, 2026-10-13, `kabuk-win/examples/desktop_thumbnail_spike.rs`):** at first the overlay drew Windows' wallpaper itself, as a bitmap read through `IDesktopWallpaper`, because the gaps between windows went black; under an animated wallpaper that bitmap is Windows' black, so the gaps went black again. A DWM thumbnail of Explorer's `Progman` shows the desktop as it is: compared with the screen read with the desktop shown, it differs by 0.0 (0-255 per channel) on Monitor 1 (main) and on Monitor 2 with a still wallpaper, and by 0.8 with the constellation playing behind the icons (the same as the scene's own change in 700 ms), against 26.9 for a black overlay. So the overlay's bottom layer is that thumbnail, live, icons included; the wallpaper bitmap is gone. Its source rectangle is in `Progman`'s own pixels (its window starts at the leftmost monitor); DWM reports the primary monitor's size as the thumbnail's source size, which is not the window's.

### D34 · Hyprland equivalents (M11): how they work and their shortcuts — Decided by the user (2026-10-13)
SPEC names the hidden workspace, tabbed window groups and an overview for M11 without saying how they work. The user approved Hyprland's way, with SPEC §6's Alt-based defaults instead of Hyprland's Super key (Win+S, Win+G and Win+Tab are Windows' own as well):
- **Hidden workspace (scratchpad):** one for the whole desk. `Alt+Shift+S` sends the focused window there (it hides); `Alt+S` shows it over the focused monitor's workspace, where its windows tile across the work area above that workspace, and hides it again; shown on another monitor, it moves to the one that asks. Moving a window to a workspace (`Alt+Shift+1…9`) takes it out. Hidden windows are recorded in the state file like any other.
- **Tabbed groups:** `Alt+G` makes the focused window a group or dissolves it; a window that opens while the group has the focus joins it as its last tab; a group takes one tile and shows one member, with a strip of tabs in the look's colours along its top (a click on a tab shows it; `Alt+Shift+G`, added by Kabuk as Hyprland binds none by default, shows the next one). Floating a member, minimising it or moving it to another workspace takes it out of the group.
- **Overview:** `Alt+O` shows every workspace of each monitor in a grid over that monitor; a click on a cell goes there, Esc or a click outside closes it. Windows does not give thumbnails of hidden windows (Kabuk hides other workspaces' windows with `SW_HIDE`, D5), so, as the user chose on 2026-10-13: the workspaces on screen show their windows as live DWM thumbnails, the others show each window in its place as a box in the look's colours with the program's icon and title. Changed on 2026-10-15 from using it: the grid holds the workspaces the bar shows (`shown_workspaces`, 4 by default, and any other with windows or on screen), each numbered under its cell, the one on screen framed on every monitor; nine empty cells said nothing.

### D33 · How Kabuk's popups come and go — Proposed (2026-10-13)
The design page's motion rule ("Hareket ve geçişler") asks for 120-220 ms, an easing curve without a bounce, opacity, place and size only: the launcher fades in growing slightly, a notice slides in 8 px. Its CSS gives the notice `transition: opacity .3s, transform .3s` but never plays it (popups use `hidden`), so the rule wins: Kabuk plays on the compositor (`IDCompositionAnimation`, cubic ease-out) a notice sliding down 8 px into place and fading in over 220 ms, the volume OSD the same upwards, and the launcher, tooltips, the tray panel and the power menu fading in from `tileIn`'s `scale(.985)` over 180 ms. A notice's window takes the 8 px of room on its incoming side, so the slide is not cut off. A leaving popup plays its entrance backwards and lets the mouse through while it does, so it never takes a click; an interrupted animation starts the next one from where it is. Popups that hold the keyboard (the launcher, the tray panel, the power menu) leave at once, so the keyboard goes straight back to the window it came from; notices, the OSD and the tooltip fade out. The OSD is redrawn in place while it shows instead of entering again. Reduced keeps only the fade; Off, Windows' "Animation effects" off, or game mode show and remove everything at once. Values in `kabuk_ui::motion`.
